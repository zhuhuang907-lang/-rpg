# 多模型协作流程

> 规程正文在 `AGENTS.md`（GLM、DS 自己找活）、`中书省/README.md`（命令、回奏、审查）、`政事堂/README.md`（议事与裁决）。这一页讲全貌。

## 一、三方与机构

| 谁 | 在哪办事 | 权 |
|---|---|---|
| 项目主人 | 提需求；对 GLM、DS 说一句「扫描仓库，干活」；真玩验收 | 一切的源头 |
| Claude | 中书省发命令；政事堂出议题、裁决；终审合并；维护知识库和技能卡 | 终审权、一票否决权 |
| GLM（zcode） | 承办命令、审查 DS 的活、在政事堂写意见 | 只推 `glm/…` 分支 |
| DS（opencode） | 承办命令、审查 GLM 的活、在政事堂写意见 | 只推 `ds/…` 分支 |

## 二、一件命令的路

```
玩家提要求 → Claude 入台账（R-编号）→ 中书省发命令「任务X（承办者）」
  → 承办者扫描仓库自己找到 → 拉 glm/task-X 或 ds/task-X → 先测试后代码 → 回奏 → 推送
  → 审查者扫描仓库自己找到 → 从承办分支拉 ds/review-X 或 glm/review-X → 审查 → 推送
  → Claude 终审：合进 claude/gallant-davinci-l8pni0、跑完整测试、对照台账 → 准 / 退回（批语）
  → 退回的：承办者在原分支改、追加「第二次回奏」，再走审查
```

## 三、定方向

```
Claude 在政事堂出议题 → GLM、DS 各自独立写意见（glm/yiti-X、ds/yiti-X）
  → Claude 裁决（政事堂/议题X/裁决.md），可一票否决 → 中书省照裁决发命令
```

## 四、为什么这样分

- **状态看远端分支就知道**，不靠谁去改一张共用的表：GLM、DS 永远不碰同一个文件，不会互相冲突。
- **诏令板、议题一览只由 Claude 改**：主分支只有一个人往里合，出了问题找得到。
- **独立写意见、交叉审查**：两个模型的毛病不一样，互相查能抓到对方的盲点；最后由 Claude 拍板，避免两边各说各的。

## 五、分支与提交

- 主开发分支 `claude/gallant-davinci-l8pni0`：只有 Claude 合并、推送（推送后自动打包发布）。
- 两个模型同时干活时，命令会把改动范围分开（不同文件或 `game.src.html` 的不同分区）。
- 提交检查（`scripts/check.sh`，git 钩子）对所有分支都一样：完整测试在当前源码上全过、护栏、规则回归、三版同一次构建、台账三栏、无 Key 无型号名。不许绕过。

## 六、需求台账条目格式

```markdown
### R-编号 一句话标题
- 来源：日期 玩家：「原话」
- 玩家验收：
  - 玩家能看到、能点到、能感觉到的结果，一条一条
- 自动验收：测试文件名（防什么）
- 状态：未做 / 在做（任务X）/ 已做，自动测试通过，玩家未验证
```

## 七、给玩家的汇报

照 `REPORT_EXAMPLE.md`：只用简体中文、玩家听得懂的话；不出现函数名、文件名、内部代号；没亲自验证的写「未验证」。
